01

What SHINE actually is

A plain–language explanation, no jargon, for anyone walking into the conversation cold.

Every quarter, a fund controller has to read a stack of draft financial statements — sometimes thirty of them — and decide whether each one is ready to go to the auditor. The work is detailed, repetitive, and unforgiving. One missed disclosure can land in an audit finding; one wrong number can land in a restatement.

SHINE is the tool the controller uses to do that work. It does not replace the controller’s judgment. It compresses the part that doesn’t need judgment — the meticulous read against the ASC 946 framework, the tie–outs, the cross–references, the comparison to prior period — so the controller spends their time on the part that does.

The acronym stands for Statement Health Intelligence and Notation Engine. The promise sits in the three words below the logo: Review · Refine · Ready.

02

How it’s built

A council of five specialists, an orchestrator that coordinates them, and a curated reference library each consults.

SHINE is intentionally decomposed. Instead of one large reviewer trying to do everything, an orchestrator dispatches five specialist subagents in two waves. Each specialist reads a small, focused slice of the FS and returns findings in a strict schema. The orchestrator merges, deduplicates, escalates, and renders.

“Each subagent is a specialist. The orchestrator is a coordinator. The split is what keeps quality high and context windows small.”

This architecture matters because it’s auditable. Every finding records which subagent produced it, which version of the prompt produced it, and which version of the reference library was consulted. A reviewer looking at a finding two quarters later can reconstruct exactly how it was generated.

03

The nine–stage review flow

From the moment the controller drops a draft, to the moment a polished report leaves the building.

01Intake
The controller hands SHINE the draft FS and supporting files
SHINE reads _REVIEW–MANIFEST.json (the per–review input list) and _FUND–METADATA.json (the static fund facts). Only the FS PDF is strictly required; everything else degrades gracefully with a controller–facing prompt.
02Identify
The cover page is verified against fund metadata
Legal name, domicile, and period are compared character–for–character. Any mismatch becomes a critical finding the controller dispositions explicitly — we don’t silently override the cover.
03Phase 1
Mechanical, Narrative, Standards run in parallel
Three specialists, three concurrent reviews. Each returns a strict JSON of findings plus a coverage manifest declaring what they checked and what they deliberately skipped.
04Phase 2
Comparative and Defense run after Phase 1 lands
They consume the Phase 1 findings as context — if Standards flagged an ASU adoption, Comparative knows to look for the matching transition disclosure.
05Aggregate
Merge, validate, reconcile, dedupe, escalate, annotate
Schema–rejects malformed findings. Reconciles clusters via specificity–scored patterns (e.g., a Level 3 reconciliation tie–out break plus a 50–2(f) gap collapse into one root cause). Escalates priors that recurred. Polishes language without overwriting the original.
06Coverage
Roll up the audit trail
100%–applicable coverage: every ASC paragraph in scope is either checked or skipped with a reason code. The controller can prove to Deloitte that nothing was silently dropped.
07Render
The dashboard appears
Statement–grouped findings, structured CFO summary, readiness banner, degradation chips. The controller’s primary interface.
08Disposition
The controller decides
Accept · Resolve · Discard · Reopen · Mark evergreen · Edit. Every action pushes to the undo stack; every state change is persisted.
09Export
A premium report leaves the building
Two modes: Preparer Edition for the fund administrator (open + accepted findings, simplified) and Audit File for Deloitte (accepted + resolved, full provenance chain, evergreen appendix). Both go through a preview–before–send modal.
The trust layer

Three things make the output defensible. Citation discipline: every standards finding cites the ASC paragraph, every regulatory finding cites the corpus key. Version stamps: every finding records the subagent, prompt and reference versions it came from. Three–field provenance: the original subagent text is immutable; polished and controller–edited versions live alongside it — reviewers see the chain.

04

How to use it — step by step

From opening the app to handing off the audit file. Eight steps; no prior knowledge required.

1

Open the app

Double–click index.html in the shine–app/ folder. Any modern browser will render it. You’ll land on the Reviews screen showing three sample reviews.

No install, no login. Everything runs in your browser — nothing leaves your machine.

2

Pick the demo review

Click the card titled AAA Coinvest Fund A LP. It’s the fully–populated example with 16 realistic findings spanning every severity, every state, recurring and evergreen markers, and a reconciler cluster.

The other two cards are list–view placeholders so you can see what a multi–fund queue feels like.

3

Read the dashboard, top to bottom

The banner tells you the readiness verdict in one word. The CFO summary below it gives five loaded lines you can paste into a committee deck. The chips surface what degraded — recurring findings, evergreen acceptances, stale references.

If the banner says Not Ready, scroll down: every critical and high finding has to be either dispositioned or evergreened before it turns green.

4

Disposition findings

Each finding card has four actions. Accept means “I agree, but the preparer hasn’t fixed it yet”. Resolve means “fixed in the next draft, audit–clean”. Discard means “false positive, doesn’t apply”. Open reveals the full drawer with evidence, citations and inline edit.

Cross 20% discard rate and SHINE will ask you to attest each one — a built–in surveillance check the audit firm will look at.

5

Use the drawer for depth

Click any finding to open the right–side drawer. You’ll see the original subagent text, the optional polished version, evidence excerpts, the cited ASC paragraph or regulatory key, reconciler constituents (if any), and a textarea where you can rewrite the language in your own voice.

The original is never overwritten. Your edit lives alongside it with an “edited” badge.

6

Mark recurring findings as evergreen

If a low or medium finding keeps coming back review after review — and you and the auditor have agreed it’s acceptable documented practice — click Mark evergreen, give it a one–line reason, and it stops escalating in future periods.

Evergreen findings still appear in the audit file export — with their justification — but they don’t block the readiness gate.

7

Export the report

Click Preparer PDF or Audit file PDF in the dashboard toolbar. A preview modal opens with a McKinsey–style report — cover, executive summary with charts, table of contents, numbered sections, appendices. Click Download PDF to save it; click Download HTML for an editable version.

Preparer mode excludes resolved and evergreen findings — what the administrator needs to act on. Audit mode includes everything with the full provenance chain.

8

Bring your own review

When you’re ready to use this on real work, click the import icon (top right) and load a findings.json produced by the SHINE skill running in Claude Code. The dashboard handles your real data the same way it handles the demo.

The schema is documented at shine–fs–review–v8/manifests/finding–schema.json.

Power user shortcuts

Ctrl+K opens the command palette · ? shows all keyboard shortcuts · A accepts the focused finding · J/K move between findings · / focuses search · Ctrl+Z undoes (up to 20 steps).

How to run it on your machine

Two paths — one for the dashboard alone, one for the full SHINE skill that produces the findings the dashboard consumes.

Path A — just the dashboard. If you only want to explore the interface or share it with someone, you don’t need anything but a browser.

# 1. Clone or pull the branch git clone <repo> git checkout claude/build-shine-v8-system-kzUiW # 2. Open the app — no install required cd shine-app open index.html # macOS start index.html # Windows # Or run a local static server if you prefer npm start # serves at http://localhost:3000

Path B — the full skill that generates real findings. SHINE is also a Claude Code skill that runs the orchestrator and five subagents against a real FS draft. The skill produces the findings.json you import into the dashboard.

# 1. Install Claude Code (CLI, desktop or web) # 2. Drop the skill folder into your skills directory cp -r shine-fs-review-v8 ~/.claude/skills/shine-fs-review # 3. For each fund you review, prepare two files # inputs/_REVIEW-MANIFEST.json — paths to FS, workbook, prior FS # _FUND-METADATA.json — static fund facts (one-time) # 4. Trigger the skill in Claude Code > SHINE this draft at /path/to/fund/draft/folder # 5. Open the resulting findings.json in the dashboard via Import
Architecture, restated

The skill at shine–fs–review–v8/ is the brain — it produces the findings. The app at shine–app/ is the workspace — the controller’s interface for dispositioning, editing, and exporting. They share the JSON schema at manifests/finding–schema.json, which is the contract between them.

When to use which path

You want to demo SHINE to your team. Path A. Send them the shine–app/ folder, tell them to double–click index.html. The demo review walks through every feature.

You want to review a real fund draft. Path B for the generation, Path A for the disposition. Run the skill in Claude Code; import the resulting findings.json in the dashboard; disposition, edit, export.

You want to share the report with the audit firm. Run Path A and use the Audit file PDF export. That’s the file you send.

Two minutes to first value

Path A takes under a minute — clone, open, click. The demo review will show every screen, every feature, every interaction. You don’t need to install anything, you don’t need Claude Code, and you don’t need a real draft FS to understand what the tool does.
