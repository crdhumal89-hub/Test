## 1. Baseline measurement

`node tools/task_harness.js --baseline`, run twice against the frozen pre-cycle app.
Both runs produced identical click counts and seconds within 0.8 percent, so the baseline
is repeatable.

| task | what a controller is doing | clicks | seconds | repeatable |
| --- | --- | ---: | ---: | --- |
| T1 | Name the SPV contributing the largest delta Pricing, and state its value | 13 | 1.23 | 13/13, 0.8% |
| T2 | State today's product NAV and whether the additive bridge ties | 1 | 0.13 | 1/1, 0.0% |
| T3 | List every SPV whose derived MV and position MV differ by more than 10 bps | **39** | 4.70 | 39/39, 0.4% |
| T4 | Load administrator marks for 12 SPVs and state the product NAV change | 2 | 0.17 | 2/2, 0.0% |
| T5 | Trace a named security to its ultimate owners and state each effective percentage | 6 | 1.43 | 6/6, 0.0% |

A "click" is any discrete user interaction: a pointer click, a committed keyboard entry,
or a scroll step. Scroll steps count because reading a 149-row table through a 654px
window is real work. Every task asserts the answer it read off the screen against an
independently computed expected answer, so a cheaper path that gets the wrong answer fails
rather than scores well.

**T3 is the outlier at 39 clicks**, three times the next worst task.

### Chosen: C1, the position-variance exception report

It is the top-ranked entry: tier 1 on correctness, and the lowest build risk of the three
tier-1 candidates. It is also the harness outlier, so the measurement and the risk argument
point the same way.

### Why each runner-up lost

- **C4** lost to C1 on build risk within tier 1, and on materiality: its worst case is
  $272k against C1's $25.5m, and the difference is already partly explained by the
  delta Pricing column.
- **C2** lost to C1 on build risk within tier 1. It is the most severe defect on this list,
  but the only fix runs through `buildBaseStruct()`, which the guardrails put out of scope,
  and it would change displayed figures. **It needs its own cycle and an explicit decision
  from the owner.** Flagged, not shipped.
- **C3** lost because it is tier 2 and no tier-2 item can outrank a tier-1 item, whatever
  the time saving. It is the strongest candidate for the next cycle after C2 is resolved.
- **C6** lost because it is tier 3.
- **C5** lost because it is tier 4 and carries near-zero value.

## 4. Target

Targeted canonical task: **T3**. Required: at least 30 percent better on clicks or seconds,
with no other task regressing by more than 5 percent on either measure.

## 5. User-facing changes shipped

Exactly these, and nothing else:

1. A new **"Position variance"** chip in the Look-Through exception strip (`#ltflags`),
   beside the existing Missing NAV / Dangling SPV / Material non-position gap chips.
   It carries no number, so the default view of the tab is unchanged numerically.
2. A **position-variance exception panel** (`#ltvarwrap`), hidden until the chip is
   pressed. It lists every SPV whose derived MV and position MV differ by more than
   10 bps, one row per SPV, with derived MV, position MV, the difference and the bps,
   sorted by absolute bps descending. It renders nothing until opened.
3. A **non-numeric variance marker** on Look-Through rows for SPVs that breach the
   threshold, so the exception is visible in the tree itself and not only in the panel.
4. The chip toggles: pressing it again closes the panel. Escape also closes it.

No existing control was moved, renamed, or removed. No keyboard path changed.

## 8. Implementation notes, not user-facing

- `assets/tracepro-phase1.js` now exports `syncFrozenOffset` on `window.__phase1`. The
  variance marker widens the identity cell, and the NAV column is pinned at that cell's
  measured width, so the offset has to be re-taken after the marker is added. Caught by the
  existing sticky-column test, which failed until the re-sync was wired in. No behaviour
  changed for anyone who is not looking at a breaching row.
- `tools/task_harness.js` converts `data-var-code` to a camelCase key. This only affects a
  code path that does not exist in the baseline app; the baseline was re-run after the fix
  and produced identical click counts (13 / 1 / 39 / 2 / 6).

## 9. Flagged for the next cycle, not shipped

**C2 is a live correctness defect and needs an owner decision.** `buildBaseStruct()` reads
an `EMB.nodes.holder` property that does not exist, so `reviseApplyNav()` builds its
structure keyed on `undefined`. Calling it with no overrides at all moves Revised MV by
$1.59m. Any controller who uploads a NAV Report today gets a wrong number with no warning.
It lost this cycle only on build risk: the fix is inside a calculation function that the
guardrails place out of scope, and it changes displayed figures. It cannot be shipped
without an explicit decision to open the engine.
